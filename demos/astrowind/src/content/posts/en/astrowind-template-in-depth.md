AstroWind starts like any template: clone it, run the dev server, see a finished site. What is different is what happens when you start changing it. Almost nothing in this site is hand-written markup for one page. Pages are data, sections are widgets, widgets are built from elements, and the look comes from a theme. This post walks through each layer, in the order you are likely to meet them.

## Pages are data

Open `src/content/pages/en/` and you will find the site as JSON files. A page is a title, a description and a list of sections, and each section names a widget and its props:

```json
{
  "widget": "Hero",
  "props": {
    "title": "Build on Astro, don't just fork it",
    "actions": [{ "variant": "primary", "text": "Get template", "href": "/pricing" }]
  }
}
```

That is the whole page format. It means a page can be edited by someone who does not write Astro, generated by a tool, or checked by the build: every widget validates its props against a schema, so a typo in a prop name stops the build with the path to it instead of silently rendering nothing. YAML works too, but JSON is the default because it is what builders and assistants write best.

## Widgets are the sections

A widget is one section of a page with one purpose: a hero, features, pricing, testimonials, a contact form. Differences of shape are props (`layout: "split"`, `layout: "cards"`), and where a widget holds other content it has named slots. The home page, the pricing page, the eight example homes and the twelve landing pages are all made from the same set, arranged differently.

Some widgets only arrange others: `Section` stacks what is inside it, `Columns` puts it side by side, `Switch` shows one option at a time. Trees stop at three levels deep on purpose; a page that needs more is usually a sign that a piece deserves to be its own widget, and a site can define one in JSON without writing code.

## Elements are the building blocks

Under the widgets sit the elements: a button, a card, a table, a dialog, a search field. They render complete, accessible HTML on the server. The ones that need behaviour upgrade that HTML in the browser as small custom elements, with no framework runtime, so a page works before any script arrives and a page that uses none ships none.

Every element names its parts with `data-part`, lists the tokens it reads, and documents its keyboard map and what happens without JavaScript. That contract is tested, which is what lets a site replace an element with its own and trust that every widget built on it still works.

## Themes are tokens

Nothing in the widgets or the elements names a colour. They ask for roles (the primary colour, the surface of a card, muted text) and the theme decides what those are, in light and in dark. Switching the theme changes the whole site without touching a component, which is also why the demo can show the same pages in several looks.

## The blog is an app

The blog is its own package that the site adds, and it brings routes, collections, a feed and search with it. It is configured by structure, not by looks:

- A preset says what kind of publication it is (personal, company, magazine, newsletter), which decides whether there are author pages or series pages.
- Views, one JSON file per page type, decide how the index, an article or an author page looks. This demo keeps the company preset and gives its index a title of its own.
- Turned-off features are not generated at all. A single-writer blog has no author pages rather than hidden ones.

Posts are Markdown files in `src/content/posts/en/`. Their headings become the table of contents, their length becomes the reading time, and their tags and category decide what "Read next" suggests.

## Where to start changing things

A practical order, from least to most code:

1. Change a page's JSON: text, images, the order of sections.
2. Change the navigation in `src/content/navigation/en/`.
3. Try another theme, or adjust the one in use.
4. Add a post, then give the blog a view of its own.
5. Only then reach for a new widget or element.

The fastest way to understand a template is still to break it on purpose. Here, breaking it usually means editing a JSON file and reading the error the build gives you, which is the point.
