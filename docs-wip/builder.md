# The visual builder

Provisional, like everything in `docs-wip/`. `@parche/builder` is the editor
for a Parche site's content: pages, layouts, menus, patterns, the design
tokens and the site config, edited in place over the site's own render.

## Running it

```bash
pnpm builder                                  # over demos/astrowind, from this repo
parche astro builder                          # in a project with @parche/builder installed
parche astro builder --root ../site --port 4400 --open
```

The command starts the site's dev server with the builder added to it and
prints the editor's address, `http://localhost:<port>/_parche/builder`.

- `--root` is the project to edit (default: the current directory).
- `--port` sets the dev server's port; `--open` opens the editor in the browser.
- `--host` listens on another address. The builder writes the project's
  files: use it only on a network you trust.

It edits the files themselves: a save writes the JSON (or Markdown) in
`src/content/`. Git is the undo across sessions.

## Dev only, by construction

- The builder is an Astro integration that only the CLI adds, through
  Astro's programmatic `dev()`. The site's `astro.config` never names it.
- It throws under any command other than `dev`, and `test/assert-dist.mjs`
  checks that no build carries `/_parche/`, preview markers or the
  builder's code.
- Every route lives under `/_parche/`. Every API call carries a session
  token generated by the CLI; the server also checks the host, the origin
  and, for writes, the content type.
- The client never sends paths, only `{ collection, id }`, resolved inside
  `src/content/`.

## The screen

- **The rail** (left) opens a panel:
  - **Documents**: pages, layouts, menus and patterns, grouped by language;
    with the blog, also its posts, views, authors, series and taxonomies.
  - **Outline**: the open document as a tree.
  - **Widgets**: the site's widgets and patterns, to drag or add.
  - **Design**: the token values.
  - **Site**: the site config.
- **The preview** (centre) is the real page, rendered by the dev server
  with the unsaved edits in place.
  - *Select* turns a click into a selection.
  - *Browse* lets the page behave, with its links kept inside the preview.
  - Device widths, and the theme and colour scheme to look at it in, sit
    above it.
- **The inspector** (right) shows the selected node's props, its wrapper and
  its issues; with nothing selected, the document's own settings. It closes
  to show the whole page and opens again for the next selection.
- **Pins.** Each side panel has a pin. Pinned, it takes its own space beside
  the preview; unpinned, it floats over the page, under the preview's
  toolbar. The documents panel starts pinned and the inspector floating;
  the choice is remembered per browser.

## What it edits

**Pages.** The tree with its slots: add, move (drag, or the arrows),
duplicate and delete nodes, only where they can go by the widget's slots
and `allow`. The props form comes from each widget's schema. A node's
wrapper is inherited from its list, none, or its own. A page's settings
are its title, description, URL, SEO and layout. Markdown pages keep
their body untouched; YAML is shown but not written.

**Layouts.** The same outline. An Outlet has a name (the unnamed one takes
the page's sections; a named one takes the page's slot of that name) and
the wrapper for the items of its list. The preview shows the layout
through a page that uses it, which can be chosen.

**Menus.** A menu's items get the form of the prop that uses it (a Header's
`links`, a Footer's columns); a menu nothing uses yet is edited as JSON. A
linked value in a form (`{ "$ref": "navigation/main" }`) opens the menu.

**Patterns** (see *Patterns* in [content-model.md](./content-model.md)):

- **New** in the Patterns list: a label, a name, the languages it serves,
  and the widget it starts from.
- **Save as pattern** on any node: the node becomes a pattern, and the
  pattern can take its place on the page.
- On a use: **Open pattern**, and **Detach**, which turns the use back into
  widgets the page owns.
- Inside a pattern, **Link to a prop** on any field of its widgets: the
  field takes the prop's value, and the prop is declared with the field's
  schema and its current value as the default. **Unlink** gives the value
  back.
- The pattern's settings list its props: rename, make required, add help,
  remove.
- A pattern previews through a page that uses it.

**The blog** (when the site has the blog parche):

- **Posts.** The frontmatter as a form: dates as dates, the image from the
  assets, the category, tags and authors suggested from what the site has.
  The body is Markdown, edited in place of the preview ("Markdown" in the
  preview's toolbar, or "Edit the text"). Title and text both show in the
  preview before a save: the body is rendered with the site's own Markdown
  pipeline. A save writes the frontmatter and leaves the rest of the file as
  it was. **New** makes a draft dated today.
- **Views.** Each page type the preset renders (index, post, author,
  taxonomy…) is listed; **Customize** copies the preset's view into
  `src/content/views/blog-<name>.json`, which the outline then edits like a
  page. `{ "$label": … }` values stay the blog's words in each language, and
  the placement rules (no ad before the title) are checked. Deleting the file
  goes back to the preset's.
- **Authors, series and taxonomies** are edited with their collection's form.
- A post previews at its address; a view at the first page that renders it.
- The blog's options (`createBlog({ … })` in `astro.config`) show in the Site
  panel, read-only.

The blog tells the builder what it needs through a module it declares for
development tools (`dev` in its manifest, reached through
`parche:registry/dev`): its schemas, its resolved config, its views and where
its pages live. The builder does not depend on the blog package.

**Design tokens.** The site's own values over the base look or over one
theme, light or dark, written to `src/parche.tokens.json`. Each token shows
its base value, what the page resolves it to now and, when the site sets
it, a reset. Changes show in the preview at once.

**Site config.** The site's JSON config, with core's schema as the form. A
save restarts the dev server, which reads it only at startup; the editor
waits for it. A site that declares its identity inline in `astro.config`
sees it read-only.

## Checks and saving

- Every document is checked as the renderer checks it: the collection's
  schema, the tree against the catalog, references, each widget's props
  with its own zod schema, and patterns (each use's props, each pattern
  against itself).
- The issues show in the outline with their paths; a click selects the
  node.
- A save writes atomically and keeps the file's indentation and key order.
  If the file changed on disk since it was opened, the save stops and asks
  which version to keep.
- Undo and redo are per document. Unsaved edits survive a reload of the
  editor.

## How the preview works

- The editor sends its unsaved documents to the server as drafts.
- The preview requests the page under `/_parche/preview/<token>/…`. The
  dev server renders it with a stand-in for `astro:content` that returns
  the drafts, and each node marks where its output starts and ends.
- A script the editor injects into the preview fetches the page again after
  each edit and morphs the body in place (Idiomorph), so scroll, focus and
  state survive. It also draws the hover and selection outlines from the
  markers.
- A Markdown draft's body is rendered to HTML with the site's Markdown
  renderer (made once when the server starts) and served with the draft.
- A page that answers 404 is tried again a few times: a document just
  created is known to the dev server only once its content is synced.
- The rest of the site, in another tab, keeps serving the saved files.

The editor itself is a prebuilt React bundle, not a page of the site's
Vite, so the dev server's reloads never touch its state.

## Known gaps

- Renaming or deleting a pattern, a menu or a layout does not update or
  warn about the documents that use it.
- The builder assumes the collections live in `src/content/<name>` and
  computes page URLs itself: a site that moves its collections or changes
  its routing is not supported yet.
- The token editor has no colour picker and no contrast check.
- A `$ref`, `$collection` or `$label` value can be opened but not chosen
  from a form.
- The preview relies on details of Astro's dev server (the `astro:content`
  stand-in, a Vite middleware): an Astro upgrade is checked against the
  builder's browser tests.
